## 一、清理缓存「没反应」

三条并存的缺陷，都在删除路径上：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `assertDeletableByCacheClear` 每次都重新解析四个区根，`zoneOf` 再解析一遍 | 每个文件 5 次 `realpath` + 8 次 path stat。20 个文件实测 **104 次 realpath**；真实 TDLib 池有上千 blob，循环长时间无任何界面反馈，看起来就是"点了没反应" | 每轮 `resolveRoots()` 一次并下传，同样 20 个文件降到 24 次 |
| 2 | `scan()` 里单个文件 stat 失败直接抛穿整个扫描，`_refreshScan` 又吞掉异常 | 设置页永远停在「正在统计…」，整块存储区像是死的 | 单文件失败不计入，不中断 |
| 3 | `integrityProbe` 抛异常会在**删除任何文件之前**终止整个清理 | 用户只看到一条失败提示，数字没变 | 记录 `integrityProbeError`，清理照常执行 |

顺带加的界面事实：不可取消的进度弹窗（`已处理 x / y` + 文件名）、`没有可清理的内容` 分支（不再让用户确认"删除 0 个文件"）、结果里的「清理前 → 清理后」、磁贴上的重新统计按钮。

一条容易踩坑的细节：`scan()` 保留 layout 派生的原始路径做占用判断，**不能**换成 canonical 路径。`/var/...` 会变成 `/private/var/...`，正在播放的文件就会显示为"未登记"，清理直接把屏上视频删掉。测试 `cache_clear_progress_test.dart` 覆盖了这条。

## 二、边下边播（方案 A）

旧的时序是硬性的：`ensureLocal()` 必须等 `is_downloading_completed`，然后整文件拷进 Documents，才交给播放器。预取只能让第二条往后变快，第一条永远等整段。

现在的路径：

```
AVPlayer ──► http://127.0.0.1:<port>/v/<token>     （RangeServer）
                     │  Range: bytes=0-
                     ▼
             FileWindow 判定可读性
                     │  download_offset ≤ p < download_offset + prefix
                     ▼
             TdStreamSource ──► downloadFile(0, 0) ──► TDLib 池文件
```

关键约束与理由：

- **只发整文件下载**（offset 0, limit 0）。带 offset 的部分下载会移动 `local.download_offset`，池文件每个字节的映射随即偏移。
- **只信 `downloaded_prefix_size`**，不信 `downloaded_size`。后者统计文件里任意位置的字节（可能带洞），按它读会读到未下载区域。
- **分块响应**（256 KB）。AVPlayer 发的是 `bytes=0-`，等整个 range 就绪等于把旧行为换个写法；分块后每块单独等 TDLib，40 MB 的 range 也能边到边发。
- **用户区不变**：播放期间后台仍跑 `ensureLocal()` 往 `Documents/TGMediaDownloads` 提一份，清理缓存依然删不掉看过的视频。
- **回环 + 随机 token**：只绑 `127.0.0.1`，路径是 128 位随机串，未知 token 返回 404。

### 回退（不可回避的一类文件）

非 faststart 的 mp4 把 `moov` 放在文件尾部，任何渐进式服务都没法提前给出。所以激活包了 6 秒超时：超时或任何异常就释放播放器，走原来那条整段下载路径。**流式失败不会比旧行为更差。**

超时那条路径只在仍持有激活 token 时才释放播放器 —— 否则会把用户已经滑到的新视频一起杀掉。
