## 1. "38" 从哪来

不是默认值、不是硬编码、也不是索引被重置。

抖音页底部的 `1 / 38` 来自 `FeedController.positionLabel`：

```dart
// 修复前
String get positionLabel => '${_index + 1} / ${_items.length}';
```

`_items` 是**当前已加载窗口**，一页 40 行、过滤掉 2 张图片后是 38。索引里那条频道有 82 条视频，但 `_items.length` 只反映这一页。

每次打开抖音页都会新建 `FeedController`（Tab 切换、返回、页面重建），`load()` 只取第一页，所以"每次都是 38"——**行为一直如此，只是标签把窗口长度当成了总数**。

修复后：

```dart
int get syncedVideos => (source as IndexFeedSource).syncedVideos; // countByChat
String get positionLabel {
  final loaded = '${_index + 1} / ${_items.length}';
  return total <= _items.length ? loaded : '$loaded · 已同步 $total';
}
```

并新增 `loadedAll`（窗口是否覆盖索引）与 `historyComplete`（索引是否还有更多页），三个概念分开：

| 名称 | 含义 | 来源 |
|---|---|---|
| 已加载 | 当前列表里有多少条 | `_items.length` |
| 已同步 | 这个频道索引里有多少视频 | `index.countByChat()` |
| 缓存文件数 | 磁盘上有多少缓存文件 | 文件系统扫描 |

`IndexFeedSource.syncedVideos` 用 `countByChat()`，与频道列表行上的数字同源，不再各算一套。

## 2. "725 停下" 从哪来

不是游标问题（游标在上一轮已改成"原始批次最老消息 id"，并有 4000 条续传测试）。这轮查到的是**调度**问题：

- `ChannelSyncEngine.syncCycle()` 每次只走 `pagesPerChannel` 页（默认 2，最多 10）；
- 调用它的地方只有：进入频道详情时的一次 `_syncMore`、下拉刷新、页脚按钮；
- 没有任何代码在**一轮结束后再叫一次**。

4000 条消息按每页 100、每轮 2 页算，需要约 20 轮。用户停留在页面上时，第 2 轮及之后从未发生，于是数字停在某一轮的结果上（报告里的 725）。

修复：新增 `lib/app/history_backfill.dart`。

| 规则 | 行为 |
|---|---|
| 单次有界 | 每次 kick 最多 8 个切片，每切片 6 页（约 4800 条消息的容量） |
| 让出事件循环 | 每个切片后 `await Future.delayed(Duration.zero)` |
| 短页才算结束 | `reachedEnd` 只在 TDLib 返回不足一页时置位 |
| 无进展即停 | 某切片 `pages == 0` 立即结束本次 kick，避免空转 |
| 单飞 | `_running` 保证同一时刻只有一个 kick；重复调用返回 `busy` |
| 触发点 | 应用启动完成后、从后台恢复时；30 秒内不重复 |
| 无定时器 | 不加循环定时任务（iOS 不会长期允许，且白耗电） |

`AppSession.syncHistorySlice()` 对**所有频道**按已存 watermark 续传，失败会返回带 `lastError` 的报告而不是抛出。

## 3. 缓存上限与自动清理

### 3.1 设置项

| 项 | 值 |
|---|---|
| 默认上限 | **1 GB** |
| 预设 | 512 MB / 1 GB / 2 GB / 5 GB |
| 自定义 | 256 MB – 20 GB，越界**拒绝保存**并提示（不静默夹取） |
| 目标 | 超过上限后清到上限的 **80%**（1 GB → 800 MB） |
| 单位 | 内部一律字节；界面 MB/GB |
| 显示 | 当前占用（缩略图/播放临时/未完成分片/池）、上限、上次清理结果 |
| 手动清理 | 保留原有按钮，未改动 |

### 3.2 清理范围（白名单，逐目录遍历）

只处理 `CacheManager.scan()` 已登记的三类：

1. `thumb/` —— 缩略图
2. `player/` —— 播放临时文件
3. `partial/` —— 未完成分片

顺序固定（先缩略图，再临时，再分片），每删 20 个让出一次事件循环；每个文件删除前过一次 `assertDeletableByCacheClear`（分区守卫），并跳过 `ActiveFileRegistry` 认为在用的文件。

**TDLib 池（`tdlib_files/`）只统计、不删除。** 理由：直接在文件系统删池文件，TDLib 的文件数据库仍认为"已完成"，下次 `getFile` 返回指向不存在文件的记录（上一轮已在解析器侧加了兜底错误，但那是兜底不是方案）。正确回收要逐文件走 TDLib `deleteFile`（该方法在只读白名单的 localOnly 里，允许使用），需要 fileId↔路径映射，本轮未实现。当三类清空后仍超限，结果明确返回"可清理目录已空，仍有 X（TDLib 文件池，暂不自动删除）"，不假装成功。

### 3.3 触发与去重

- 启动完成、从后台恢复（`_runMaintenance`，30 秒节流）；
- 单飞：`AutoCacheCleaner._running`，重复调用返回 `busy`；
- 后台不做无限清理：仅在系统给的恢复窗口里跑一次，下次启动再查。

### 3.4 与播放的关系

- 在播/被播放器持有的文件在 `ActiveFileRegistry` 中，跳过；
- 预加载产物落在 `player/` 或池里；`player/` 中的文件若未被标记在用，会被清——但预加载路径缓存只保存路径字符串，下次解析会重新校验文件存在性并重新获取（上一轮已实现），不会把死路径交给播放器；
- 清理不会删除当前播放需要的池文件（池根本不删）。

## 4. 数量、索引、缓存三者关系（本次专项检查）

| 问题 | 结论 |
|---|---|
| 频道列表的视频数从哪来 | `IndexStore.countByChat(videosOnly: true)`，一次遍历 `_records`，与缓存文件无关 |
| 抖音页的"总数"从哪来 | 修复前是 `_items.length`（已加载窗口）；现在是 `countByChat()` + 窗口分开显示 |
| 缓存文件数 | 只由 `CacheManager.scan()` 统计，不参与任何视频计数 |
| 清理会不会删索引 | 不会：扫描范围仅三类临时目录；索引在 `Application Support/tgmedia/index`（`indexDb` 分区，守卫拒绝删除） |
| 清理会不会重置同步游标 | 不会：游标存在索引里，清理不触碰 |
| 清理后视频还能播吗 | 能：记录还在，缓存没了 → 解析器 `stat` 显示未完成/文件不存在 → 重新 `downloadFile` |
| 清理会不会触发全量同步 | 不会：`syncCycle(resume: true)` 从 watermark 继续；清理不改变 watermark |

有专门的测试把这四条钉住（见 §5 `feed_counts_test.dart`）。
